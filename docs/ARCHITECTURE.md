## 0 · 问题的特殊性

常规 GUI Agent 的隐含假设是：**动作只改变目标状态**。

本项目的环境打破了这个假设。Android 的无障碍框架在**动作分发路径**上绑定了单焦点语义 ——
任何通过 a11y 发出的动作，都会把全系统唯一的 window 焦点夺到目标窗口。
（实测覆盖 6 个动作类型，`result=false` 时同样夺焦点，见 `experiments/EXPERIMENTS.md` E4 / B1。）

所以这个 Agent 的动作有三重后果：

| 后果 | 说明 |
|---|---|
| 改变目标状态 | 常规后果，符合预期 |
| **破坏用户的输入链路** | 主屏失焦 → 用户打字中断 |
| **可能污染自己的工作区** | 用户击键会灌入副屏有焦点的输入框（实测 +330 字符） |

第三条是正确性问题，不是体验问题 —— Agent 会基于被污染的状态继续决策。

**因此 loop 中必须有两个常规 Agent 没有的环节：补偿（焦点归还）与再观测（不信任动作前的世界模型）。**

## 1 · 验收标准的定义

> **用户当前正在进行的交互不被中断。**

以「持续打字」作为最严苛的验证场景 —— 它对焦点的依赖最强。
通过它，弱依赖焦点的场景（滚动、浏览、观看）是其子集。

**为什么不用「零打扰」**：该表述无法证伪（总能找到更细的感知维度：帧率、触摸延迟、GPU 占用），
不构成可测量的判据。「当前交互不中断」有明确的观测方式和失败信号。

### 三级现象分类

| 现象 | 归类 | 处理 |
|---|---|---|
| 焦点短暂丢失（10–15 ms） | 可接受 | 无需处理 |
| 用户需手动点回输入框才能继续 | 打扰，尽量避免 | 归还 + 重试 |
| **用户击键灌入副屏工作区** | **正确性故障** | 必须避免 |

三者由同一机制解决：归还成功则同时消失。因此「归还必须发生」的理由等级是正确性，不是体验。

## 2 · 核心分层：护栏与策略

架构的中心决策是把职责切成两层，**并让两层之间的缝可以移动**。

### 护栏层（不可协商，harness 强制执行）

- 焦点归还必须发生，且与动作原子绑定
- 每个动作后必须做轻量自检
- 每轮观测前必须做状态自检
- 归还失败必须上报，不得静默

**这些不交给 LLM 决定。** 理由不是模型不够聪明，而是失败模式的代价不对称：
归还缺失会导致用户输入污染 Agent 工作区，属于安全边界。
概率性决策者（无论多强）都会漏、会被长 trajectory 稀释、会被 prompt 干扰。

### 策略层（可配置，LLM 或规则均可承担）

- 选择下一个动作
- 失败后如何绕路
- 是否等待用户输入空隙再执行（礼貌等级）
- 何时判定任务完成

### 缝的位置随基座模型能力移动

| 基座模型 | 策略层实现 |
|---|---|
| 小参数量本地模型 | 策略写成固定规则，LLM 只做动作选择 |
| 强模型（Sonnet / DeepSeek V4 等） | 环境异常、打扰累积等信息全部暴露，由 LLM 自行权衡 |

**护栏层在两种情况下完全相同。** 换模型只改缝的位置，不改护栏 ——
这是「架构撑得起更复杂任务」的具体含义，也是这套 harness 与具体模型解耦的方式。

> 注意区分**可见性**与**可控性**：归还结果对模型可见（甚至应该可见），
> 但归还是否执行永远不由模型决定。

## 3 · 执行循环

```
观测 → 规划 → 执行 → 验证 → （回到观测）
```

四个环节中只有「规划」属于策略层。

### 3.1 观测（护栏）

1. dump 副屏节点树（`getWindowsOnAllDisplays()`）
2. 压缩为 locator 条目（见 §4）
3. **状态自检**

状态自检至少覆盖：

- 副屏是否存在（display id 每次都变，必须动态解析）
- 目标 app 是否仍在副屏上
- 树是否是新的（根节点 hash / 时间戳）
- 主屏是否存在 IME 窗口（用户是否正在输入）

> **为什么自检是护栏而非优化**：实验期间人工反复踩到同一类坑 ——
> 以为 app 在副屏、实际已被回收；以为 dump 是新的、实际是缓存。
> Agent 会踩一模一样的坑，且不会像人一样起疑。

### 3.2 规划（策略）

LLM 单步决策，每轮输出一个动作。

**为什么单步而非多步计划**：

1. 本环境中动作会改变窗口结构，多步计划的中途失效概率显著高于常规场景
2. 单步 loop 天然每步重新观测，无需额外的计划失效检测机制
3. 失败可恢复性更好 —— 选错一步，下一轮 LLM 看到新状态自行纠正
4. 演示价值：loop 本身可见，观众看到的是决策过程而非脚本回放

代价：延迟与 token 成本更高。实测数据 _（待填）_

### 3.3 执行（护栏）

**动作与归还绑成不可分割的原子单元。**

```
1. 解析 locator → 副屏目标节点
2. 记录主屏输入焦点节点的「定位信息」（不是节点对象）
3. 执行动作
4. 用定位信息重新解析主屏节点 → performAction(ACTION_FOCUS)
5. 失败则重试一次
6. 返回 { action_ok, restore_ok, restore_ms, ... }
```

**第 2 步与第 4 步是关键**：归还目标必须在动作后**重新解析**，不能复用动作前的节点快照。

> 依据：B1 实测 —— 触发全局主题变更的动作会导致所有 Activity 重建，
> 动作前抓取的 `AccessibilityNodeInfo` 快照失效（`refresh()` 返回 false），
> 归还原语拿到一具死快照，无从分发。
> 对照组（无全局副作用的开关）`refresh()` 成功，归还有效 ——
> 因果确定在「副作用」而非「动作类型」。

**归还原语为什么用 `ACTION_FOCUS`**：

主屏输入框的 **view 焦点从未丢失**（`isFocused` 仍为 true），丢的只有 **window 焦点**。
对已聚焦节点再发 `ACTION_FOCUS` 是空操作、返回 `false` ——
但抢焦点发生在**动作分发路径**，与动作是否生效无关，因此 window 焦点被拉回主屏。

> **同一机制，E4 中是故障，E6 中是手段。**
> `ACTION_FOCUS` 之所以是最优归还原语，恰恰因为它什么都不做：
> 零 UI 副作用、不移动光标（实测 `sel` 前后一致），是一个纯焦点拉取操作。

### 3.4 验证（护栏）

**轻量自检，判据由 harness 按节点类型自动推断，不要求 LLM 声明预期。**

| 目标类型 / 动作 | 自检判据 |
|---|---|
| Switch / Checkbox + CLICK | `checked` 是否变化 |
| EditText + SET_TEXT | `text` 是否等于写入值 |
| SCROLL | 可见节点集合是否变化（取若干 text 做 hash） |
| 其他 CLICK | Activity / 包名是否变化 |
| LONG_CLICK | 窗口数量是否变化 |

共同点：**只需重读目标节点或窗口元数据，无需 dump 整棵树。**

完整验证（dump + 压缩 + 交由 LLM 判断"是否达成意图"）属于策略层，仅在步骤边界执行。

**为什么不信任 tool 返回值**：已实测三种"工具会撒谎"的形态 ——

1. `performAction` 返回 true 但界面无反应（哑动作）
2. `uiautomator dump --display N` 返回成功但参数被静默忽略
3. 测量工具本身失准：丢字计数器锁定在常量上，**稳定输出"丢字 0"这个正确答案**

第 3 条是最危险的一类：正确答案 + 错误来源。因此验证必须**独立重新观测**，
不能复用产生该结果的同一条链路。

## 4 · 观测层：locator 抽象

### 问题

LLM 需要引用节点，但 `resource-id` 既不保证存在，也不保证唯一：

- Compose 无 View 对象实例 → 无 id，`className` 默认 `android.view.View`
- WebView 的 id 常为运行时生成的哈希
- 即使传统 View：Preference 框架中真正可点的容器 `id=null`，
  而带 id 的 TextView `clickable=false`
- 列表中同一 id 重复 N 次

> 曾一度以「规范 `resource-id` 覆盖率」衡量节点树可用性，据此判定 Compose / WebView 应用不可用。
> **该指标是错的** —— 无障碍树保证提供的是读屏软件必需的部分
> （`text` / `contentDescription` / 状态位 / `actionList`），`resource-id` 不在其中。
> 反证：TalkBack 在 Compose 应用上工作正常，而它从不使用 `resource-id`。
> 修正后的指标：**可交互节点中能被唯一指认的比例。**

### 分层降级定位

| 层级 | 策略 | 条件 |
|---|---|---|
| L1 | `resource_id` | 存在且在当前树内唯一 |
| L2 | `resource_id` + `text` | id 重复 |
| L3 | `content_desc` | 无 id，desc 唯一 |
| L4 | `text` + `class_name` | text 唯一 |
| L5 | `text` + 同类序号 | text 重复 |
| L6 | 结构路径 | 以上全无 |

唯一性判断在**当前这棵树的范围内**完成，不作全局假设。

### 锚点合并

节点树中反复出现的模式：文字在子节点、可点在父节点。

```
[LinearLayout] ''  clickable=true   id=null
    [TextView] 'Magnification'  clickable=false
```

必须合并为一个逻辑条目，且 locator 描述的是**如何找到可执行的那个节点**，而非文字节点。

> 依据：实测中 `findAccessibilityNodeInfosByText("Dark theme")` 命中两个节点
> （TextView 与 Switch），取首个并向上找 clickable → 命中整行容器 → **进入子页面**；
> 而按 id 精确命中 Switch → **原地翻转开关**。同一文字，两种完全不同的行为。

### 呈现给 LLM 的形式

```
[3] Magnification | clickable | 当前值 Off
[4] Dark theme    | switch    | 当前值 On
```

**LLM 只与短 ID 和语义打交道，不接触 resource-id、坐标、类名等实现细节。**
locator 的解析、降级、消歧全部由 harness 承担。

换 app、换模型，这一层的接口不变。

## 5 · Action space

| 动作 | 参数 | 归还有效性 |
|---|---|---|
| `click` | target | ✅ 实测有效 |
| `set_text` | target, value | ✅ 实测有效 |
| `scroll` | target, direction | ✅ 实测有效 |
| `long_click` | target | ✅ 实测有效 |
| `focus` | target | ✅ 实测有效 |
| `back` | — | _（待测）_ |
| `wait` | condition, timeout | 无动作，不涉及归还 |

**已知边界**：触发全局配置变更（主题、语言、字体大小、旋转）的动作会导致所有 Activity 重建，
归还快照失效。此类动作标记为「已知归还失败」，执行时必须上报，不禁用但需谨慎。

### LLM 输出格式

```json
{
  "thought": "需要先进入网络设置页面",
  "action": "click",
  "target": 3,
  "value": null,
  "done": false
}
```

## 6 · Observation 的组织

单步规划下，每轮给 LLM 的内容：

```
## 任务
<目标描述>

## 环境状态
- 副屏: display 6 · com.android.settings ✓
- 主屏焦点: 已归还 (12 ms)
- 用户输入中: 是
- 上一步异常: 无

## 当前界面
[0] Navigate up | clickable
[1] Brightness level | clickable | 0%
[2] Dark theme | switch | On
...

## 已执行
1. click "Network & internet" → ok，页面变为 SubSettings
2. scroll down → ok
3. click "Wi-Fi" → ok，归还失败（窗口重建）
```

三点设计：

1. **历史是结构化文字摘要，不是历史节点树** —— 省 token，且旧树全是噪声
2. **「环境状态」独立成节**，与动作结果分开。常规 Agent 的失败只有"动作没生效"，
   本项目多了一整类"动作生效了，但环境被自己破坏了"
3. **异常按偏离报告**：`restore_ok=true` 时只留摘要，`restore_ok=false` 时必须显式标记。
   observation 应报告偏离，而非报告正常 —— 弱模型不被噪声淹没，强模型出事时拿得到线索

### 终止条件

LLM 输出 `done: true` **且** 硬步数上限（防止卡死，演示不能无限循环）。

完成条件常是语义的（"邮件已发出"），需要 LLM 判断；硬上限是工程兜底。

## 7 · 部署形态

```
┌──────────── PC / 云端（Python）────────────┐
│  Planner (LLM) · 历史管理 · 终止判断        │
│  Locator 解析 · 树压缩 · 验证判据推断        │
└────────────────┬──────────────────────────┘
                 │ adb broadcast / socket
┌────────────────┴──────────────────────────┐
│      Android（Kotlin，~400 行）            │
│  AccessibilityService                      │
│  · 跨 display 读取节点树                    │
│  · 执行动作 + 焦点归还（原子）               │
└───────────────────────────────────────────┘
```

副屏由 scrcpy `--new-display` 创建的 VirtualDisplay 承载。

> **为什么是 scrcpy 而非 `overlay_display_devices`**：实测 overlay 创建的 simulated display
> 对无障碍服务完全不可见（同一服务、同一 flag、同一次运行下的对照），
> 而 scrcpy 的 VirtualDisplay 可被 `getWindowsOnAllDisplays()` 完整读取。
> 两种虚拟屏在无障碍框架中待遇不同 —— 该差异未见于官方文档。

分工原则：**Android 侧只做感知与执行，不做规划、不做状态管理、不调 LLM。**
