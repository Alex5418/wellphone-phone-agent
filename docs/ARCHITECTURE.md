## 0 · 问题的特殊性

常规 GUI Agent 的隐含假设是：**动作只改变目标状态**。

本项目的环境打破了这个假设。Android 的无障碍框架（下文一律简写 **a11y** ——
`a` + 中间 11 个字母 + `y`，即 `accessibility`；同 `i18n` / `l10n` 的构词法。
本项目里它专指 `AccessibilityService` 那套 API：`AccessibilityNodeInfo`、
`performAction`、`getWindowsOnAllDisplays` 等）在**动作分发路径**上绑定了单焦点语义 ——
任何通过 a11y 发出的动作，都会把全系统唯一的 window 焦点夺到目标窗口。
（实测覆盖 6 个动作类型，`result=false` 时同样夺焦点，见 `experiments/EXPERIMENTS.md` E4 / B1。）

所以这个 Agent 的动作有三重后果：

| 后果 | 说明 |
|---|---|
| 改变目标状态 | 常规后果，符合预期 |
| **破坏用户的输入链路** | 主屏失焦 → 用户打字中断 |
| **可能污染自己的工作区** | 用户击键打字会灌入副屏有焦点的输入框（E7 定量：不归还时 120 字里 56 个，且无上界）。**限外接键盘** ——  |

第三条是正确性问题，不是体验问题 —— Agent 会基于被污染的状态继续决策。

**因此 loop 中必须有两个常规 Agent 没有的环节：补偿（焦点归还）与再观测（不信任动作前的世界模型）。**

## 1 · 验收标准的定义

> **用户当前正在进行的交互不被中断。**

以「持续打字」作为最严苛的验证场景 —— 它对焦点的依赖最强。
通过它，弱依赖焦点的场景（滚动、浏览、观看）是其子集。

**为什么不用「零打扰」**：该表述无法证伪（总能找到更细的感知维度：帧率、触摸延迟、GPU 占用），
不构成可测量的判据。「当前交互不中断」有明确的观测方式和失败信号。

### 三级现象分类

| 现象 | 归类 | 处理 |
|---|---|---|
| 焦点短暂丢失（10–15 ms） | 可接受 | 无需处理 |
| 用户需手动点回输入框才能继续 | 打扰，尽量避免 | 归还 + 重试 |
| **用户击键灌入副屏工作区** | **正确性故障** | 必须避免 |

> ⚠ **E12 实测暴露的缺口**：焦点 8/8 归还成功、双链路一致，用户**仍然**要手动点一次
> 才能继续打字（软键盘被收起）。
> **我们归还的是 window 焦点，用户需要的是"能继续打字" —— 两者不等价。**
> `ACTION_FOCUS` 拉得回窗口焦点，拉不回已被收起的 IME。
> 而且 loop 每步只在开头采一次 `ime_present`，这次收起 + 用户自行恢复正好落在采样之间，
> **整条 trajectory 全绿，唯一发现它的是用户本人**。
> 已在 `act` 响应里逐次记录键盘状态（`ime.before/after/dismissed`）。
> **E18 复算了全部落盘数据：45 步带该字段，`dismissed` 一次都没为真** ——
> 而收起确实发生过。原因是这个仪表只在**单次 `act` 内**采两点，
> 而四次能定位的消失**没有一次落在那个窗口里**（两次在观测/LLM 期间，
> 其中一次前一步压根没有动作；一次在两次 act 之间；一次消失后又自行恢复）。
> **不是「尚未捕获」，是采样点选错了位置，结构上抓不到。**
> 采样间隔就是 LLM 延迟（实测单步 1.5–149 s），用十几秒的窗口归因毫秒级事件不成立。
> 见 `experiments/E12-GMAIL-DEMO.md` 与 `experiments/E18-IME-DISMISSAL-ATTRIBUTION.md`。

三者由同一机制处理：归还。但 E7 实测表明**归还不能让它们"同时消失"**，
只能把第三条从「无上界」压成「与打扰窗口成正比」：

| 输入方式 | 条件 | 落进 agent 工作区 | 丢字 |
|---|---|---|---|
| 物理键盘 | 不归还 | **56 / 120**（此后每个字都是，无上界） | 0 |
| 物理键盘 | 归还（窗口 205–612 ms） | **6–21 / 120**（≈ 窗口 ÷ 打字速率） | 0 |
| 物理键盘 | 主屏本就无焦点持有者 | **120 / 120**（无还可归） | 0 |
| **软键盘** | 归还 / 不归还都试了 | **0**（点屏幕这一下自己把焦点带回来了） | 0 |
| **软键盘** | 全局配置变更（窗口 1364 ms） | 0 | **6 / 15** |

**按输入方式分级**（E8）：外接键盘下第三级现象（污染）真实存在，归还是正确性要求；
软键盘**逐字提交**时污染从未出现、且路径自愈。

**但中文输入法暴露了一个归还挡不住的损伤面**（E9 → 经 E10 更正）：
拼音在上屏前处于 composing 态，**副屏发生窗口 / Activity 变更时**，主屏的 IME 会
`finishComposingText` 把未上屏的拼音强制提交（分段空格消失、候选上下文清零）。

关键在于**决定因素是动作类型，不是归还开关**：滚动类动作（不产生窗口变更）从不打断；
导航点击会打断 —— 但**只在不归还时打断**。纯粹的焦点抢夺本身不打断中文输入。

> **更正（E11 推翻 E10 此处）**：本节原写「归还只能降低概率、不能消除（实测 3 次仍破 1 次）」，
> 那是 E10 的 n=3。E11 把四格各重跑到 n≥20 并修掉起点丢字问题，结果是
> **nav × restore=true 打断 0/20**，阳性对照 nav × restore=false 为 10/20（50%）。
> E10 该格自己标注过「最不准」。按 n=20 的数据，**归还在这一格是消除，不是削弱**。
> 适用范围：composetest · Gboard 拼音 · nav / scroll 两类动作。
> **会重建 Activity 的动作类未测** —— 见下方缺口。见 `experiments/E11-RESULTS.md`。

> ⚠ **矩阵仍缺一格。** composing 打断（本节）只测过 scroll / nav；
> 击键落进副屏（§8.1）由 E15 测过输入类与重建类。两个矩阵拼起来，
> **「composing 打断 × 重建 Activity 类动作」从未测过** ——
> 而 Gmail 这类需要输入的任务必然包含「点开撰写页」这种重建动作。
> 演示录制时观察到主屏拼音被提交过一次，**单次观察、未定量、无对照**，
> 正落在这一格。记为未知，不并入上面的 0/20。

> **对 IME 中间态，破坏是二值的：断了，或没断 —— 与打扰窗口长短无关。**
> 导航点击的打扰窗口只有 8–20 ms，远在 `DISTURB_BUDGET_MS`（500 ms）之内，照样打断输入。

**因此打扰窗口预算管不住这一类破坏。** 需要另一条尚未实现的判据：
副屏动作若会引起窗口 / Activity 变更，且主屏正处于 IME composing 态，
则该动作有打断用户输入的风险 —— **而归还挡不住它**。
处置方式（推迟动作 / 把 `wait` 从礼貌升级为护栏 / 接受并写明损伤面）
是一个**尚未做出的架构决策**，见 `experiments/E10-COMPOSING-BREAK-CAUSE.md` §5。

所以「归还必须发生」的理由等级是正确性，不是体验；
而「打扰窗口必须短」是同一条要求的定量形式 —— 污染字符数正比于它。
减少污染的唯一途径是缩短窗口（见 §5 ⛔ 排除项与 `DISTURB_BUDGET_MS`）。

## 2 · 核心分层：护栏与策略

架构的中心决策是把职责切成两层，**并让两层之间的缝可以移动**。

### 护栏层（不可协商，harness 强制执行）

- 焦点归还必须发生，且与动作原子绑定
- 每个动作后必须做轻量自检
- 每轮观测前必须做状态自检
- 归还失败必须上报，不得静默

**这些不交给 LLM 决定。** 理由不是模型不够聪明，而是失败模式的代价不对称：
归还缺失会导致用户输入污染 Agent 工作区，属于安全边界。
概率性决策者（无论多强）都会漏、会被长 trajectory 稀释、会被 prompt 干扰。

### 策略层（可配置，LLM 或规则均可承担）

- 选择下一个动作
- 失败后如何绕路
- 是否等待用户输入空隙再执行（礼貌等级）
- 何时判定任务完成

### 缝的位置随基座模型能力移动

| 基座模型 | 策略层实现 |
|---|---|
| 小参数量本地模型 | 策略写成固定规则，LLM 只做动作选择 |
| 强模型（Sonnet / DeepSeek V4 等） | 环境异常、打扰累积等信息全部暴露，由 LLM 自行权衡 |

**护栏层在两种情况下完全相同。** 换模型只改缝的位置，不改护栏 ——
这是「架构撑得起更复杂任务」的具体含义，也是这套 harness 与具体模型解耦的方式。

> **观测层同样不随模型能力浮动。** E13 实测：弱模型在 Gmail 任务上卡死，换强模型能过 ——
> 但那不是模型能力问题，是观测层把浮层 / 下拉拍平成了普通条目，
> **没有表达「某些条目刚消失、某些刚出现」**。补上这条信息后，同一个弱模型
> **8 步完成**（比强模型还少），LLM 延迟从 65.6s 降到 10.9s。
>
> 推论：**harness 的质量应该由弱模型来检验。** 强模型会用推理补上观测的缺口，
> 从而掩盖缺陷 —— 代价是 6 倍延迟和对模型能力的隐性依赖。

> 注意区分**可见性**与**可控性**：归还结果对模型可见（甚至应该可见），
> 但归还是否执行永远不由模型决定。

## 3 · 执行循环

```
观测 → 规划 → 执行 → 验证 → （回到观测）
```

四个环节中只有「规划」属于策略层。

### 3.1 观测（护栏）

1. dump 副屏节点树（`getWindowsOnAllDisplays()`）
2. 压缩为 locator 条目（见 §4）
3. **状态自检**

状态自检至少覆盖：

- 副屏是否存在（display id 每次都变，必须动态解析）
- 目标 app 是否仍在副屏上
- 树是否是新的（根节点 hash / 时间戳）
- 主屏是否存在 IME 窗口（用户是否正在输入）

> **为什么自检是护栏而非优化**：实验期间人工反复踩到同一类坑 ——
> 以为 app 在副屏、实际已被回收；以为 dump 是新的、实际是缓存。
> Agent 会踩一模一样的坑，且不会像人一样起疑。

### 3.2 规划（策略）

LLM 单步决策，每轮输出一个动作。

**为什么单步而非多步计划**：

1. 本环境中动作会改变窗口结构，多步计划的中途失效概率显著高于常规场景
2. 单步 loop 天然每步重新观测，无需额外的计划失效检测机制
3. 失败可恢复性更好 —— 选错一步，下一轮 LLM 看到新状态自行纠正
4. 演示价值：loop 本身可见，观众看到的是决策过程而非脚本回放

代价：延迟与 token 成本更高。实测数据 _（待填）_

### 3.3 执行（护栏）

**动作与归还绑成不可分割的原子单元。**

```
1. 解析 locator → 副屏目标节点
2. 记录主屏输入焦点节点的「定位信息」（不是节点对象）
3. 执行动作
4. 用定位信息重新解析主屏节点 → performAction(ACTION_FOCUS)
5. 失败则重试一次
6. 返回 { action_ok, restore_ok, restore_ms, ... }
```

**第 2 步与第 4 步是关键**：归还目标必须在动作后**重新解析**，不能复用动作前的节点快照。

> 依据：B1 实测 —— 触发全局主题变更的动作会导致所有 Activity 重建，
> 动作前抓取的 `AccessibilityNodeInfo` 快照失效（`refresh()` 返回 false），
> 归还原语拿到一具死快照，无从分发。
> 对照组（无全局副作用的开关）`refresh()` 成功，归还有效 ——
> 因果确定在「副作用」而非「动作类型」。

**归还原语为什么用 `ACTION_FOCUS`**：

主屏输入框的 **view 焦点从未丢失**（`isFocused` 仍为 true），丢的只有 **window 焦点**。
对已聚焦节点再发 `ACTION_FOCUS` 是空操作、返回 `false` ——
但抢焦点发生在**动作分发路径**，与动作是否生效无关，因此 window 焦点被拉回主屏。

> **同一机制，E4 中是故障，E6 中是手段。**
> `ACTION_FOCUS` 之所以是最优归还原语，恰恰因为它什么都不做：
> 零 UI 副作用、不移动光标（实测 `sel` 前后一致），是一个纯焦点拉取操作。

### 3.4 验证（护栏）

**轻量自检，判据由 harness 按节点类型自动推断，不要求 LLM 声明预期。**

| 目标类型 / 动作 | 自检判据 |
|---|---|
| Switch / Checkbox + CLICK | `checked` 是否变化 |
| EditText + SET_TEXT | `text` 是否等于写入值 |
| SCROLL | 可见节点集合是否变化（取若干 text 做 hash） |
| 其他 CLICK | Activity / 包名是否变化 |
| LONG_CLICK | 窗口数量是否变化 |

共同点：**只需重读目标节点或窗口元数据，无需 dump 整棵树。**

完整验证（dump + 压缩 + 交由 LLM 判断"是否达成意图"）属于策略层，仅在步骤边界执行。

### 通则：所有仪表都是三值的

**成立 / 不成立 / 读不到 —— 不许折叠成布尔。**

这条是从同一个错误反复出现里总结出来的。已经踩到四次：

| # | 现象 | 折叠方式 |
|---|---|---|
| 1 | `uiautomator dump --display N` 返回成功但参数被静默忽略 | 「命令成功」当成「按我说的做了」 |
| 2 | 丢字计数器锁在常量上，稳定输出正确答案 | 「读到了数」当成「读到了对的数」 |
| 3 | `findByText` 的查找宇宙与压缩器不一致，序号错位 | 「找到了节点」当成「找到了那个节点」 |
| 4 | 主屏焦点持有者读不到 → 报「归还失败」（D1 实测，其实成功了） | 「读不到」当成「不相等」 |

共同结构：**仪表的失败被读成了被测对象的失败。** 代价不对称 ——
假失败会让 Agent 基于错误前提改变行为，而"未知"至少诚实。

落实到代码：`restore.ok`、`tree.hash_mismatch`、`state.ime_present`
都是 `true / false / null` 三值；`verify` 的结论是 `PASS / FAIL / UNKNOWN` 三态；
`adbutil` 读不到一律返回 `None`。**没有证据说明失败时，不许报失败。**

**为什么不信任 tool 返回值**：已实测五种"工具会撒谎"的形态 ——

1. `performAction` 返回 true 但界面无反应（哑动作）
2. `uiautomator dump --display N` 返回成功但参数被静默忽略
3. 测量工具本身失准：丢字计数器锁定在常量上，**稳定输出"丢字 0"这个正确答案**
4. 仪表测的根本不是那条链路：`dumpsys gfxinfo` 在视频**正在播放**时恒读 0 帧 ——
   硬件加速视频由 SurfaceFlinger 直接合成，不进 app 的 HWUI 管线（E14）
5. 字段是懒更新的快照：`media_session` 的 `position` 在 `state=PLAYING speed=1.0`
   时走 89ms 就冻住不动 —— 它带 `updated=` 时间戳，app 只在事件时推送（E14）

第 3 / 4 / 5 条是最危险的一类：**读数看起来完全合理，而且往往正好支持你预期的结论**。
E14 里 `position` 不动"恰好"支持"视频被打断了"—— 不验证仪表就会拿到一个想要的假阳性。
因此：**先用已知的阳性 / 阴性状态标定仪表，再相信它的读数**；
验证必须**独立重新观测**，不能复用产生该结果的同一条链路。

## 4 · 观测层：locator 抽象

### 问题

LLM 需要引用节点，但 `resource-id` 既不保证存在，也不保证唯一：

- Compose 无 View 对象实例 → 无 id，`className` 默认 `android.view.View`
- WebView 的 id 常为运行时生成的哈希
- 即使传统 View：Preference 框架中真正可点的容器 `id=null`，
  而带 id 的 TextView `clickable=false`
- 列表中同一 id 重复 N 次

> 曾一度以「规范 `resource-id` 覆盖率」衡量节点树可用性，据此判定 Compose / WebView 应用不可用。
> **该指标是错的** —— 无障碍树保证提供的是读屏软件必需的部分
> （`text` / `contentDescription` / 状态位 / `actionList`），`resource-id` 不在其中。
> 反证：TalkBack 在 Compose 应用上工作正常，而它从不使用 `resource-id`。
> 修正后的指标：**可交互节点中能被唯一指认的比例。**

### 分层降级定位

| 层级 | 策略 | 条件 |
|---|---|---|
| L1 | `resource_id` | 存在且在当前树内唯一 |
| L2 | `resource_id` + `text` | id 重复 |
| L3 | `content_desc` | 无 id，desc 唯一 |
| L4 | `text` + `class_name` | text 唯一 |
| L5 | `text` + 同类序号 | text 重复 |
| L6 | 结构路径 | 以上全无 |

唯一性判断在**当前这棵树的范围内**完成，不作全局假设。

### 锚点合并

节点树中反复出现的模式：文字在子节点、可点在父节点。

```
[LinearLayout] ''  clickable=true   id=null
    [TextView] 'Magnification'  clickable=false
```

必须合并为一个逻辑条目，且 locator 描述的是**如何找到可执行的那个节点**，而非文字节点。

> 依据：实测中 `findAccessibilityNodeInfosByText("Dark theme")` 命中两个节点
> （TextView 与 Switch），取首个并向上找 clickable → 命中整行容器 → **进入子页面**；
> 而按 id 精确命中 Switch → **原地翻转开关**。同一文字，两种完全不同的行为。

### 呈现给 LLM 的形式

```
[3] Magnification | clickable | 当前值 Off
[4] Dark theme    | switch    | 当前值 On
```

**LLM 只与短 ID 和语义打交道，不接触 resource-id、坐标、类名等实现细节。**
locator 的解析、降级、消歧全部由 harness 承担。

换 app、换模型，这一层的接口不变。

## 5 · Action space

| 动作 | 参数 | 归还有效性 |
|---|---|---|
| `click` | target | ✅ 实测有效 |
| `set_text` | target, value | ✅ 实测有效 |
| `scroll` | target, direction | ✅ 实测有效 |
| `long_click` | target | ✅ 实测有效 |
| `focus` | target | ✅ 实测有效 |
| `back` | — | _（待测）_ |
| `wait` | condition, timeout | 无动作，不涉及归还 |

### ⛔ 排除项：触发全局配置变更的目标

主题 / 语言 / 字体大小 / 显示大小 / 旋转 —— **这一族目标排除出动作空间，harness 拒绝执行。**

依据是 D1 实测（`experiments/D1-FIRST-REAL-RUN.md`）：

| 动作 | 打扰窗口 |
|---|---|
| `scroll` | **12 ms** |
| 切换深色主题（全局配置变更） | **2526 ms** |

差两个数量级。瓶颈是「动作后重新解析主屏焦点节点」：**补了子时间戳的单步重跑**
（`D1-restore-timing-breakdown/`，与上表那次三步任务不是同一次 run，所以两个数不构成分解）
里，这一项独占 **2962 ms** ——
全局配置变更会让所有 Activity 重建，对主屏窗口的跨进程 a11y 查询一直阻塞到对端能应答；
真正发 `ACTION_FOCUS` 只用了 225 ms。**瓶颈不在归还原语，在重解析。**

按 §1 的验收标准（用户当前正在进行的交互不被中断），3 秒是**硬失败**，不是边界。
而且按 B1 附带发现 A，这 3 秒里用户的击键会流向副屏当前有焦点的输入框 ——
副屏那一页恰好停在输入框上时就是数据污染，属正确性故障。

这修正了 B1 的表述：不是「归还失败」，是「归还成功但很慢」。改成动作后重新解析之后
归还确实会成功，代价是打扰窗口涨到 ~3 s。

**排除的判据不是动作名，是目标**（`harness/policy.py`，两条并用）：

1. 静态名单：标签匹配 + 目标是开关类。**必然不完备** —— 换语言、换 app 就会漏，
   它减少已知伤害，不提供保证。导航进入这些设置页（button）不拦：进页面不改配置。
2. 实测预算：任何一步实际打扰窗口超过 `DISTURB_BUDGET_MS`（500 ms）即拉黑并上报。
   这一条与语言、与 app 都无关 —— 它量的就是我们真正在乎的那个东西。

被排除的条目**仍然呈现给 LLM**，只是标 `⛔ 不可操作` 并附原因。藏起来的话
LLM 只会一直找它；给出理由，它可以据此判定任务无法完成。

> 未验证的优化方向：给重解析设截止时间 + 先盲发一次 `ACTION_FOCUS`。
> 它牺牲的正是「归还目标必须在动作后重新解析」这个已验证的正确性前提，需单独实验，先不做。

### LLM 输出格式

{
  "thought": "需要先进入网络设置页面",
  "action": "click",
  "target": 3,
  "value": null,
  "done": false

## 6 · Observation 的组织

单步规划下，每轮给 LLM 的内容：

```
## 任务
<目标描述>

## 环境状态
- 副屏: display 6 · com.android.settings ✓
- 主屏焦点: 已归还 (12 ms)
- 用户输入中: 是
- 上一步异常: 无

## 当前界面
[0] Navigate up | clickable
[1] Brightness level | clickable | 0%
[2] Dark theme | switch | On
...

## 已执行
1. click "Network & internet" → ok，页面变为 SubSettings
2. scroll down → ok
3. click "Wi-Fi" → ok，归还失败（窗口重建）
```

三点设计：

1. **历史是结构化文字摘要，不是历史节点树** —— 省 token，且旧树全是噪声
2. **「环境状态」独立成节**，与动作结果分开。常规 Agent 的失败只有"动作没生效"，
   本项目多了一整类"动作生效了，但环境被自己破坏了"
3. **异常按偏离报告**：`restore_ok=true` 时只留摘要，`restore_ok=false` 时必须显式标记。
   observation 应报告偏离，而非报告正常 —— 弱模型不被噪声淹没，强模型出事时拿得到线索

### 终止条件

LLM 输出 `done: true` **且** 硬步数上限（防止卡死，演示不能无限循环）。

完成条件常是语义的（"邮件已发出"），需要 LLM 判断；硬上限是工程兜底。

## 7 · 部署形态

```
┌──────────── PC / 云端（Python）────────────┐
│  Planner (LLM) · 历史管理 · 终止判断        │
│  Locator 解析 · 树压缩 · 验证判据推断        │
└────────────────┬──────────────────────────┘
                 │ adb broadcast / socket
┌────────────────┴──────────────────────────┐
│      Android（Kotlin，约 1700 行）          │
│  AccessibilityService                      │
│  · 跨 display 读取节点树                    │
│  · 执行动作 + 焦点归还（原子）               │
└───────────────────────────────────────────┘
```

副屏由 scrcpy `--new-display` 创建的 VirtualDisplay 承载。

> **为什么是 scrcpy 而非 `overlay_display_devices`**：实测 overlay 创建的 simulated display
> 对无障碍服务完全不可见（同一服务、同一 flag、同一次运行下的对照），
> 而 scrcpy 的 VirtualDisplay 可被 `getWindowsOnAllDisplays()` 完整读取。
> 两种虚拟屏在无障碍框架中待遇不同 —— 该差异未见于官方文档。

分工原则：**Android 侧只做感知与执行，不做规划、不做状态管理、不调 LLM。**

## 8 · 适用边界

### 8.1 一条换实现也绕不过去的边界：单一 IME 输入连接

这是本方案已知的**唯一架构级缺陷**，且它**不是无障碍带来的**。

先把两件常被混为一谈的事拆开：

| | 谁造成的 | 现状 |
|---|---|---|
| **window 焦点被夺走** | a11y 的动作分发绑定单焦点语义 | **a11y 特有，且已解决** —— 归还与动作原子绑定，实测 12–300 ms，dumpsys 独立链路交叉校验 |
| **IME 的 `InputConnection` 改绑到副屏编辑器** | **编辑器获得输入焦点**这件事本身 | **未解决，且换实现也绕不过去** |

第二条的证据（`dumpsys input_method`，API 34 模拟器）：

```
mCurMethodId       = LatinIME                        ← 全系统一个 IME 实例
mCurClient         = ClientState{...}                ← 单数：同一时刻只有一个客户端被绑定
mCurTokenDisplayId = 0
```

`mCurClient` 是**单数**。副屏那个新编辑器一拿到输入焦点，IMMS 就把绑定移过去，
用户在主屏软键盘上的下一次点击于是写进了副屏的输入框
（[E15](experiments/E15-SECONDARY-FIELD-CONTAMINATION.md)：重建副屏 Activity 时 9/79 命中，
`restore=true` 全程开着也挡不住 —— **归还的是 window 焦点，撤销不了输入连接的改绑**）。

**关键推论**：让编辑器获得输入焦点是"往输入框写字"的前提。
所以换 UIAutomator、换 root、换事件注入，**只要共用同一个输入域就一样会改绑**。
这不是"a11y 方案绕不过去"，是**任何共用输入域的方案都绕不过去**。

### 8.2 那什么样的载体能绕过

判据只有一条：**副屏的工作区要有独立的输入域**（不只是独立的 display —— display
焦点我们已经有了，`FLAG_OWN_FOCUS` 让 `mCurrentFocus` 每屏一个，问题不在那里）。

| 路径 | 可行性 |
|---|---|
| work profile / private space | ❌ **解决的是错的那一层**。它隔离数据与应用，不给独立输入焦点域 |
| 可见后台用户（多屏多用户，Android 14 为车机加的） | ❌ 本设备明确不支持：<br>`dumpsys user` → `Supports visible background users on displays: false`。手机 form factor 默认关闭 |
| VirtualDeviceManager（Android 13+ Companion Device 串流线） | ❓ 概念上最对口 —— 虚拟设备有自己的输入路由。**未实测**，需要配套权限 |
| 两台设备 / 云设备 | ✅ 物理隔离必然有效，但那已不是「副屏 agent」这个产品形态 |

**结论**：在手机 form factor 上，目前没有既保持本产品形态、又能消除这条缺陷的路径。
它应被当作**平台约束**上报，而不是当作待修的实现缺陷。

### 8.3 其余边界

- 节点树质量是硬前提；不同 UI 技术栈的可指认率对照见 [C2](experiments/C2-RELIABILITY.md)
- Compose 应用里 `findFocus()` 返回 `android.view.View` 包装节点、`editable=false`，
  真正的 EditText 在树里 —— 只信 `primary_focus.editable` 会时灵时不灵
- 需登录、验证码、支付、生物识别的流程不在范围内 —— 属流程壁垒，不是树的问题
- 部分应用会检测无障碍服务并拒绝服务
- 触发全局配置变更的动作已排除出动作空间（§5 ⛔）
- **仅在模拟器 API 34 验证，未在真机复现**
