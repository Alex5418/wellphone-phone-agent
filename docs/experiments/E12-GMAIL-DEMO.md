# E12 · 真实任务端到端：用户在主屏打中文，agent 在副屏发邮件

**日期** 2026-08-06 · **标签** `[非root可复现]` · API 34 · 模拟器 · scrcpy VirtualDisplay
**副屏** Gmail 2023.04（真实 Google 账号）· **主屏** composetest + Gboard 中文拼音
**模型** `deepseek-v4-pro`（策略层）· **trajectory** `runs/2026-08-06T16-51-30/`

这是本项目第一个**有外部可验证结果**的端到端任务：邮件真的到达收件箱 ——
一条与 harness 完全无关的验证链路。

---

## 1 · 结果

| | |
|---|---|
| 任务 | 给指定地址发邮件，指定主题与正文 |
| 步数 | 12 步（含 3 次 `wait`），161 秒 |
| 结果 | `done`，**邮件到达，正文正确**（人工在收件箱确认） |
| 焦点归还 | **8/8 成功**（设备侧 + dumpsys 双链路一致） |
| 打扰窗口 | 8 次合计 **2183 ms**，中位数 180 ms，最大 1036 ms（Gmail 冷启动） |
| 用户输入 | 期间打进 **145 个中文字符**，选词提交全程正常 |

### ⚠ 但验收标准没有干净通过

用户报告：**打字过程中软键盘被收起过一次，需要手动点一次才能继续。**

按 ARCHITECTURE §1 的三级分类，这正是第二级：

| 现象 | 归类 | 本次 |
|---|---|---|
| 焦点短暂丢失（10–15 ms） | 可接受 | — |
| **用户需手动点回才能继续** | **打扰，尽量避免** | ← **发生了** |
| 用户击键灌入副屏工作区 | 正确性故障 | 未发生 |

**任务成功 ≠ 验收通过。** 这一条必须分开说。

## 2 · 核心发现：归还的定义太窄

焦点 **8/8 全部归还成功**，`focus_action_result=true`、`holder_after` 与 dumpsys 一致 ——
按我们现有的判据，这一轮**毫无问题**。但用户仍然被打断了。

> **我们归还的是 window 焦点；用户需要的是"能继续打字"。两者不等价。**
> 焦点还回去了，软键盘没回来 —— 用户照样得动手。

这是护栏定义上的缺口，不是实现 bug：`ACTION_FOCUS` 拉回窗口焦点，
但**不会**让已被收起的 IME 重新弹出。E11-2 的"点回输入框 IME 也不弹回"
是同一件事的另一面。

## 3 · 为什么 trajectory 里看不到

loop 每步只在**开头**采一次 `ime_present`，而这次收起 + 用户自己点回来，
正好落在两次采样之间 —— 12 步的 env.json 里 `ime_present` **全都是 true**。

**唯一发现它的是用户本人。** 一个只有人能看见、仪表全绿的伤害，
正是这个项目最该防的那类东西。

### 已做的修正

设备侧在 `act` 响应里逐次记录键盘状态：

```json
"ime": {"before": true, "after": true, "dismissed": false}
```

**限度**：该探针已实现并在真机上返回合理值，但**尚未捕获到一次真实的收起**
（复现时轻量点击 73 ms、导航点击 25 ms 都没收键盘）。所以它"能报"是验证过的，
"报得准"还没有。

## 4 · 未定位的部分

哪个动作收起了键盘 —— **没查出来**。已排除：轻量按钮点击（73 ms）、
Gmail 内导航点击（25 ms）。剩下的嫌疑是那次 1036 ms 的冷启动点击，或 `Send`
（它会关闭撰写页）。没有继续追，因为：

1. 复现需要精确重建当时的状态（Gmail 冷启动只有第一次）
2. 更该做的是让它可被观测，而不是猜是哪一次

## 5 · 顺带确认的三件事

**① 正文的假阴性第三次确认。** 第 8 步 `set_text` 判 **FAIL**，LLM 之后没有重写正文
就直接发送 —— **收到的邮件正文完全正确**。写入成功、读取通道滞后，
判据给出了假阴性（见 E12 §7 的形态清单）。

**② 礼貌层在真实场景下自主生效三次。** 模型根据 observation 里的「用户输入中: 是」
自己选择让路：

```
1. wait → 用户正在主屏输入中文，当前不紧急，等待一下让用户操作完成
4. wait → 用户正在输入，填写主题不紧急，等待一下避免打扰
9. wait → 用户正在输入中，此时点击输入框可能会打断用户的击键
```

第 11 步它又明确权衡后选择执行：「虽然用户正在输入，但这是最后一步动作，直接执行」。
**没有人教它这些**，`wait` 只是动作空间里的一个选项。

**③ 实测打扰预算护栏当场开火。** 第 2 步 Gmail 冷启动打扰 1036 ms > 500 ms 预算，
`policy` 立即把 "Compose" 拉黑：

```
[blocked] ⚠ 打扰窗口 1036 ms 超出预算 500 ms —— 已把 "Compose" 排除出动作空间
```

这不是设计时预演的场景，是真实数据触发的。

## 6 · 模型能力决定了任务成败，护栏一行没改

同一任务先用 `deepseek-v4-flash` 彩排：

| | flash | pro |
|---|---|---|
| 结果 | 卡死中止（连续 4 步界面无变化） | 11 步完成 |
| 卡在哪 | 填完收件人后自动补全下拉遮住 Subject，没识别出 `[9] Alex` 是待确认的建议 | 第 2 步就点掉了 |
| token | 8192 被推理占满两次 | 16384 够用 |

**护栏层完全相同，只有策略层换了。** 这是 ARCHITECTURE §2「缝的位置随基座模型能力移动」
的一次现场演示 —— 而且它省掉了一次不必要的观测层改造：
原本准备给观测加层级信息（让 LLM 看出 `Alex` 属于补全列表），换模型后发现不需要。

## 7 · 侦查阶段踩到的三个坑（都在正式跑之前）

1. **通知权限弹窗**把 Gmail 挡住十分钟，无障碍读到的 root 一直是 null，
   表现为"副屏有窗口但没有节点"。新装/新登录的 app 第一次启动必须先人工过一遍系统弹窗。
2. **收件人自动补全会把 Subject 顶掉** —— 必须先点补全建议把地址变成 chip。
   这是本任务真正的难点，也是弱模型翻车的地方。
3. **正文字段的无障碍读取滞后一次写入**（`refresh()` 无效、等 3–5 秒无效）。

第 3 条是"工具会撒谎"的**第八种形态**，且是新类型：
前七种是"读到了错的东西"，这一种是"**读到的是过去的东西**"。

## 8 · locator 在真实 app 上的表现

| 字段 | 策略 | 结果 |
|---|---|---|
| Send | L1（`id/send`） | ✅ |
| Subject | L1（`id/subject`） | ✅ |
