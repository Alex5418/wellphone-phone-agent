# E14 · 主屏看视频时，副屏 agent 夺焦点会不会打断播放

**日期** 2026-08-07 · **标签** `[非root可复现]` · API 34 · 模拟器
**主屏** display 0 · Chrome · m.youtube.com 播放中 · **副屏** display 3 · SecondaryDisplayLauncher
**脚本** `tools/exp_video_disturbance.py`

E7–E13 全部测的是**打字**场景 —— 最严苛、强依赖焦点的那一类。
题面还有一条「不抢画面 · 用户屏幕不卡不跳」，而**观看类场景一直只有推论没有实测**。
推论是"没有键盘就没有键盘可收"，但有一个具体的反面依据：
**部分 app 在 `onWindowFocusChanged(false)` 时会暂停自身逻辑**（视频 / 游戏类常见）。
主屏失焦时播放会不会停，只能测。

---

## 1 · 仪表的选择：四个候选，三个被证伪

这一节比结论本身更值得看。**先验证仪表，再相信读数**。

| 候选仪表 | 判定 | 依据 |
|---|---|---|
| `dumpsys gfxinfo <pkg>` | ❌ **不能用** | 硬件加速视频由 SurfaceFlinger 直接合成，不进 app 的 HWUI 管线。视频**正在播**时它读出 0 帧 —— 用它会得到"0 掉帧 = 完全不卡"这个**漂亮的假结论** |
| `dumpsys SurfaceFlinger --latency '<layer>'` | ❌ **读不到** | 图层名能拿到（`SurfaceView[com.android.chrome/…](BLAST)#1426`），但本机模拟器上取不到有效帧时间戳。**读不到就不用，不硬凑** |
| `media_session` 的 `position` | ❌ **不能用** | 实测懒更新：`state=PLAYING speed=1.0` 时 position 走了 89ms 就冻在 346383 不动。它是带 `updated=` 的快照，app 只在事件时 `setPlaybackState` |
| `media_session` 的 `state` | ✅ 用 | 直接回答"有没有变成 PAUSED" |
| **主屏截图 md5**（设备上算） | ✅ 用 | 不依赖任何图形加速路径 |

截图哈希这个仪表**先做了对照验证**再投入使用：

```
== 播放中 ==   cbf71705dcfd  5999d513b3f8  0fe0d852f1f7  862d601423f7   ← 4 个全不同
== 暂停后 ==   f844e512e9ad  f844e512e9ad  f844e512e9ad  f844e512e9ad   ← 4 个完全相同
```

这是第 10、11 例「工具会撒谎」（见 `随手记.md`）。
第三例尤其值得记：`position` 不动**看起来**正好支持"视频被打断了"这个我预期的结论 ——
**如果不去验证仪表，它会给我一个我想要的假阳性。**

### 先验（两项都必须过，否则拒绝启动）

`state == PLAYING` **且** 4 次采样中 ≥3 个不同画面指纹。
视频没在真播时测出来的"没暂停"没有意义 —— 这条不能为了让脚本跑起来而放宽。

> 补记：先验一开始确实过不了，一度怀疑是模拟器加速。**截图后发现视频屏幕上就是暂停的**，
> 大播放键在正中间，停在 5:46/25:55。仪表没撒谎，是我没看屏幕。

## 2 · 结果

| 分组 | 归还焦点 | 动作 | 单次打扰窗口 | 采样 | 出现过的状态 | PAUSED | 最长画面冻结 |
|---|---|---|---|---|---|---|---|
| **A** 对照 | — | 0 | — | 33 | `PLAYING` | **0** | **0.0s** |
| **B** 护栏 | ✅ true | 8 | 489–1481ms | 27 | `PLAYING` | **0** | **0.0s** |
| **C** 阳性对照 | ❌ false | 8 | 1–17ms | 34 | `PLAYING` | **0** | **0.0s** |

B 组的打扰窗口 489–1481ms，**比此前 Settings 上测到的 12–300ms 大一个量级**
（副屏是 launcher 的 Apps list，重解析主屏节点更慢）。也就是说这一轮的条件**更严苛**，
负结果因此更强，不是因为打扰太轻才没测出来。

## 3 · 阳性对照的有效性自证

「没暂停」只有在**确实夺走了焦点**的前提下才有意义。C 组跑完（restore=false，从未归还）立刻查：

```
Display: mDisplayId=0   mCurrentFocus=null                     ← 主屏，Chrome/YouTube 在这
Display: mDisplayId=3   mCurrentFocus=…SecondaryDisplayLauncher ← 焦点在副屏
```

主屏**连焦点窗口都没有**。在这个状态下继续采样：

```
state=PLAYING(3)   2d96f78a0c79
state=PLAYING(3)   5dd922c4873f
state=PLAYING(3)   5cc3a9673ce1
```

**主屏完全失焦，视频照播，画面照变。**

## 4 · 结论

> **Chrome 里的 YouTube 网页版不因窗口失焦而暂停。**
> 在主屏 `mCurrentFocus=null` 持续存在的情况下，播放状态始终为 PLAYING，画面持续更新。
> 因此在"用户在看视频"这类场景下，agent 夺焦点**没有产生可观测的打扰**。

配合 E7–E13：

| 用户在干什么 | 是否有可感知打扰 | 依据 |
|---|---|---|
| 中文输入法打字 | ⚠️ **软键盘会被收起一次**，需手动点一次恢复 | E9–E12，用户实测 |
| 打字（击键落点） | ✅ 无 —— 0/20 丢字、0/20 串到副屏 | E11 n=20 |
| **看视频** | ✅ **无** | 本实验 |
| 浏览网页（不打字） | 未单独测；与看视频同属"不持有输入焦点"，推论无打扰 | 推论，非实测 |

**唯一确认的用户可见代价仍然只有一个：打字时软键盘会收起一次。**

## 5 · 限度（这些没测到，不能声称）

- **测的是"暂停 / 长冻结"，不是"微卡顿"。** 采样间隔 1.2–1.6s，冻结阈值取 2.5×间隔（3–4s）。
  一次几十毫秒的掉帧本实验**看不见** —— 而唯一能看见它的仪表（帧级）正是读不到的那个。
  所以本实验支持的是"不会停"，**不能**升级成"一帧都不掉"。
- 只测了 1 个 app（Chrome 里的 YouTube 网页版）、每组 1 次。
  别的播放器（尤其原生 app、游戏）完全可能在失焦时自行暂停 —— 这是 app 的行为，不是 harness 能控的。
- 副屏动作目标是 launcher 的 Apps list，不是一个真实任务流程；测的是**夺焦点这件事本身**。
- 模拟器，无真机。
- `restore_confirmed_by` 返回 `None`（未确认归还来源），但 `dumpsys` 侧已独立验证焦点确实回到了
  display 0 的 Chrome，结论不依赖那个字段。

## 6 · 环境备忘

Windows 上 `adb forward tcp:8760` 报
`cannot bind to 127.0.0.1:8760 … (10013)` —— 端口落在 Hyper-V 的保留段里（重启后常见）。
harness 已支持 `PHONEAGENT_PORT` 覆盖：

```bash
adb forward tcp:18760 localabstract:phoneagent
PHONEAGENT_PORT=18760 python tools/exp_video_disturbance.py --arm B
```
