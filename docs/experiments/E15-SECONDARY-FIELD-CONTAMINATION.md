# E15 · 软键盘击键会不会落进副屏的输入框 —— 未能复现，判定为未知

**日期** 2026-08-07 · **标签** `[非root可复现]` · API 34 · 模拟器
**主屏** composetest（中文输入法，鼠标点软键盘）· **副屏** display 4 · Gmail 撰写页
**脚本** `tools/exp_secondary_contamination.py`

---

## 1 · 起因：E8 的结论是全称的，条件却不是

E8 测软键盘路径，八组污染全是 0，并给了机制解释：

> IME 连接绑在主屏编辑器上，失焦时解绑，不会转投到副屏；
> 副屏带 `FLAG_OWN_FOCUS`、自成 display group，主屏的 IME 本来也够不到它。

**但那八组的副屏跑的是 Settings —— 那一页没有输入框。**
E7 §4 早就写下了伏笔：「没有污染是因为副屏那一页没有输入框 ——
若有，这 129 个就会变成污染。」E8 把一个条件结论写成了全称结论。

2026-08-07 一次真实 run 撞上了那个没测过的格子
（`runs/2026-08-07T03-52-37/step-03/`）：

```
act_req   value = "alexw769829@gmail.com"      ← agent 只写了 21 字符
probe     text  = "alexw769829@gmail.comge"    ← 多出 'ge'，光标 sel=23
          focused: true                         ← 副屏 EditText 持有编辑焦点
restore   holder_after = composetest，dumpsys 交叉校验一致 ✓   disturb_ms = 788
```

`ge` 是拼音片段，用户当时正用**鼠标点软键盘**打中文。若属实，
E8 的全称结论与 README 的「软键盘 0 污染」都要改。

## 2 · 设计：只隔离一个变量

三组**都停在同一个 Gmail 撰写页**，同一动作类型、同一 restore 设置。
唯一差别是 agent 聚焦的目标是不是编辑器 —— 不换 app、不换动作，
所以任何差异只能来自这一个变量。

标记字符取 `x`：任务文本、邮箱地址、Gmail 界面文案里都不出现它，出现即外来。

## 3 · 中途修掉的两个仪表缺陷

**这一节是本实验最该看的部分。** 第一版三组全 0，但那三个 0 都不作数：

### 3.1 有效性判据太弱，我自己的脚本犯了同一类错

第一版判据是「主屏文本末值 ≠ 起始值」。**你在开头敲一串然后停手，它照样判有效** ——
而动作窗口里没有击键时读到 0 是必然的。

改成看**相邻采样之间主屏文本长度有没有增长**，多数间隔都在增长才算数，
并把增量数组打出来。修完之后数据才硬：每 3 秒稳定增长 22–56 字。

### 3.2 动作类型不对，窗口小了一个数量级

首次观测发生在 `SET_TEXT`、`disturb_ms=788`。第一版用 `FOCUS` 复跑，
窗口只有 3–33ms。**那不是阴性结论，是条件没对上。**
（这条退路是开跑前就写好的，不是事后找的台阶。）

## 4 · 结果

| 分组 | 副屏被聚焦的目标 | 动作 | restore | 打扰窗口中位 | n | 多余字符 |
|---|---|---|---|---|---|---|
| A | 按钮（非编辑器） | FOCUS | true | 31 ms | 8 | **0** |
| B | To 输入框 | FOCUS | true | 33 ms | 8 | **0** |
| C | To 输入框 | FOCUS | false | 3 ms | 8 | **0** |
| B′ | To 输入框 | SET_TEXT | true | 86 ms | 8 | **0** |
| C′ | To 输入框 | SET_TEXT | false | 7 ms | 8 | **0** |
| D | To 输入框（每轮**重新获得**焦点） | 失焦→CLICK→SET_TEXT | true | 212 ms | 10 | **0** |

**合计 50 次测量机会，一次都没复现。** B′/C′/D 的有效性两项全过
（主屏持续增长、每次都有 disturb_ms）。

D 组是针对「机制在瞬态而非稳态」这个假设专门加的：
B/C 是对着一个**已经聚焦**的框反复写，若 IME 的改绑发生在
「编辑器获得焦点的那一刻」，稳态里根本没有这个转换。D 每轮重建该转换，仍然 0。

### 附带对照：没人打字时也不会多出字符

原始那次写的是真实邮箱地址，会触发 Gmail 的联系人自动补全；上面几组写的是
`READY`，不触发。补一组**无人打字 + 写真实地址** ×6，读回全部干净、零多余字符。

→ **`ge` 不是 Gmail 自动补全或 SET_TEXT 实现的产物。**

## 5 · 结论：未知，不是不成立

> 50 次未能复现，`ge` 的来源**判定为未知**，作为待解异常记录在案。

不写成「不存在」—— 那是把「读不到」折成「不成立」，正是 ARCHITECTURE §3
反复在防的那件事。也不写成「存在」—— 1 次对 50 次，证据不够。

### 本实验确实排除掉的条件

这些不再是猜测：

- 「副屏有聚焦的编辑器」**本身不足以**造成污染（B/B′ 各 8 次，0）
- 「副屏有聚焦编辑器 + 焦点整轮不归还」**也不足以**（C/C′ 各 8 次，用户连敲 200+ 字，0）
- 「编辑器反复重新获得焦点」**也不足以**（D 10 次，0）
- 不是 Gmail 自动补全，也不是 SET_TEXT 实现本身（无人打字对照 6 次，0）

也就是说：不管 `ge` 从哪来，**它需要的条件比"副屏有输入框"窄得多**。
E8 §4.1 的机制解释虽然是从一个不完整的条件集推出来的，
但在本实验覆盖到的所有条件下它都成立。

## 6 · 限度

- **打扰窗口没覆盖到原始量级**：本实验最大 440ms，中位 212ms；原始是 **788ms**。
  若机制与窗口长度相关，最关键的那一段没测到。
- 没有复现原始那次的**完整 LLM 驱动序列**（click → 补全下拉浮层出现 → set_text）。
  自动补全浮层出现时的窗口是唯一还没排查的明显差异，要继续追就从这里入手。
- 只在一个 app（Gmail）、一台模拟器上测；无真机。
- 用户的打字节奏无法标定 —— 「一直在点」只由主屏文本增长速率间接证明。

## 7 · 对其他文档的影响

- **README 的「软键盘 0 污染」那一行保留**（E8 8 组 + E15 50 次，共 58 次为 0），
  但限度里必须写明这条异常。
- **E8 §4.1 的措辞要收窄**：它的结论只在其覆盖的条件下成立，不是全称。
- 首次观测的那份 trajectory 保留在 `runs/2026-08-07T03-52-37/`，不要删 ——
  它是这条异常唯一的原始证据。
