# E16 · 污染率 vs 打扰窗口：`DISTURB_BUDGET_MS = 500` 一次也没拦住

**日期** 2026-08-07 · **标签** `[非root可复现]` · API 34 · 模拟器
**主屏** composetest（Gboard 拼音，`input tap` 自动敲键）· **副屏** Gmail 撰写页
**脚本** `tools/exp_secondary_contamination.py --arm E --auto`
**原始数据** `data/e16-{S,M,L}.csv`（逐次落盘的 `(disturb_ms, hit)` 配对）
**执行** 前 79 次由 `deepseek-v4-pro` 按 `briefs/SUBTASK-E16-DOSE-RESPONSE.md` 完成；
L 组由我补跑。全部数据独立复算过。

## 1 · 要回答的问题

[E15](E15-SECONDARY-FIELD-CONTAMINATION.md) 确认了软键盘击键会落进副屏输入框
（条件：agent 重建副屏 Activity；`restore=true` 挡不住），但留下一个空白：
**命中和打扰窗口长度有没有关系？**

线索很弱：E15 的 E 组两次命中恰好是十次里窗口最大的两个，n 太小。

这件事值钱是因为 `DISTURB_BUDGET_MS = 500` 的立论依据就写在 `config.py` 里：

> 依据：D1 实测滚动 12ms、全局配置变更 2526ms —— **中间没有灰色地带**。

**如果灰色地带存在，这个阈值就是拍出来的。**

## 2 · 结果（n=99，全部 `--arm E`，即每轮重建 ComposeActivity）

| 打扰窗口 | 迭代数 | 命中 | 命中率 |
|---|---|---|---|
| 0–200 ms | 67 | **0** | **0.0 %** |
| 200–300 ms | 13 | 1 | 7.7 % |
| **300–500 ms** | 17 | **8** | **47.1 %** |
| >500 ms | 2 | 0 | 样本不足，见 §5 |

**九次命中的窗口：272 / 314 / 337 / 364 / 375 / 383 / 389 / 397 / 431 ms。**

### 头条

> **灰色地带存在，就在 270–430 ms —— 而九次污染没有一次超过 500 ms。**
> `DISTURB_BUDGET_MS = 500` 对它们的灵敏度是 **0**。

`config.py` 里那句"中间没有灰色地带"被证伪。那句话是从 **Settings 一个 app 的两个动作**
推出来的（12 ms 与 2526 ms），而灰色地带在别的 app 上是存在的。

### 分组

| 组 | 主屏文本规模 | n | 命中 | 窗口中位 | 窗口范围 |
|---|---|---|---|---|---|
| S | 每轮前清空到 <50 字 | 40 | 5 | 121 ms | 45–410 ms |
| M | 不清空，自然堆积 | 39 | 4 | 120 ms | 30–1144 ms |
| L | 开跑前堆到 353 字 | 20 | 0 | 138 ms | 84–439 ms |

**L 组的自变量操纵失败了**，见 §5。分桶表跨组合并是因为自变量是窗口本身，
分组只是拉开窗口的手段 —— 而这个手段没起作用。

## 3 · 这个参数测的是代理变量，而且是最弱的那个

把 E14 / E15 / E16 拼起来，伤害由三个因素共同决定：

| 因素 | 证据 | 效应 |
|---|---|---|
| ① **用户当时在干什么** | E14：主屏 `mCurrentFocus=null` **持续存在**时视频照播，三组 0 暂停 0 冻结 | 看视频时窗口再长也无害 |
| ② **动作有没有重建副屏编辑器** | E15：不重建 **0/70**，重建 **5/30**；动作数 / 写入值 / restore 全对齐时 **0/10 vs 3/20** | **因果判据** |
| ③ **窗口时长**（← 本参数） | 本实验：<200 ms **0/67**，300–500 ms **47%** | 只在 ①② 都成立时起作用 |

`DISTURB_BUDGET_MS` 只捕捉了 ③ —— 三者里最弱、且**条件依赖**的一个。
把一个三元函数压成标量阈值，于是两头都不准：

- **灵敏度差**：9 次污染全在阈值以下，一次没抓到
- **特异度差**：Gmail 上把 `Compose`(871 ms) / `Send`(2322 ms) / 正文框(1052 ms) 全拉黑，
  而那是任务必需的三个动作（见 `runs/2026-08-07T05-52-07`）

**漏掉真阳性，同时拦住必需动作。**

### 为什么会这样：慢的动作和会污染的动作是同一批

`Compose` 开新 Activity → 871 ms；`Send` 关掉它 → 2322 ms；普通 `set_text` 不重建 → 120 ms。
**窗口长度是「这个动作重建了东西」的代理**，不是原因。在代理变量上做二分，
必然同时产生假阴性（重建了但窗口没超）与假阳性（窗口超了但只是主屏节点树大、重解析慢）。

## 4 · 重设计方向（设计建议，**不是实测结论**）

判据从「窗口时长」换成「**副屏 Activity / 编辑器是否被重建**」：

- 它是**因果的**（E15 已隔离变量证明）
- 它**本来就在观测**：每步都记 `activity` 与 `tree_hash`
- 它与语言、与 app 无关，这一点和原设计的初衷一致

`disturb_ms` 的**测量**必须保留 —— 没有它，本项目所有关于"不打扰"的话都是自说自话。
要去掉的是「超阈值就永久拉黑」这个反应，不是这个仪表。

**本节未经实验验证，不得当作结论引用。**

## 5 · 限度

- **L 组的自变量操纵失败。** 设计假设"堆大主屏文本 → 重解析变慢 → 窗口变长"，
  实测把主屏堆到 353 字后窗口中位仍是 138 ms，与 S(121)/M(120) 无区别。
  所以 L 组只是又添了 20 个低窗口样本，**不是高窗口样本**。
- **`>500 ms` 未表征（n=2）。** 这一格决定一件要紧的事：
  - 若命中率**继续升高** → 关系单调，阈值这个**形式是对的**，只是 500 定高了
  - 若命中率**掉回 0** → 关系是一条**带**，阈值这个形式根本不适用，调数字没用
  - **决定性实验**：主屏换成重应用（Chrome，实测能产生 871/2322 ms 的窗口）重跑 `--arm E`，
    判据是 >500 ms 桶的命中率方向。**未做**，因为环境不稳且不影响本文头条结论。
- **只有下界是可执行的。** 「<200 ms 时 0/67」给出一个安全下界；
  上界未知不改变工程动作（把窗口压下去）。
- 敲键器有一个盲区：**键盘一旦被收起，`input tap` 的坐标会落到底下的 UI 上**。
  L 组第 2 轮就是这么废的 —— 退格键坐标砸到了 composetest 的 `Send` 按钮，
  主屏文本被清空（屏幕上留着 `Message sent`）。该轮已作废，不计入统计。
- 一次模拟器 ANR（SystemUI 两屏都弹）→ 冷重启。重启前后的数据未混合统计。
- 只有一个 app（Gmail）、一台模拟器、无真机。
- 阳性命中不依赖有效性判据（副屏里的标记字符只可能来自敲键器）；
  阴性才依赖。作废轮次里若有命中仍计入 —— 本实验作废轮次无命中。
