# E18 · 软键盘收起是哪个动作干的 —— 查不出来，而且我知道为什么查不出来

**日期** 2026-08-09 · **标签** `[无需设备]` · 只读已落盘的 trajectory
**脚本** `tools/scan_ime_transitions.py`（可反复复算）
**数据源** `runs/*/step-*/env.json` 与 `act_resp.json`，126 步

---

## 1 · 要回答的问题

E12 留下一条**唯一确认的用户可见代价**：软键盘会被收起一次，用户需手动点一次才能继续打字。
README「状态与限度」写着「尚未定位到具体是哪个动作触发」。

为此已经装了仪表 —— `act` 响应里逐次记录 `ime.before / ime.after / ime.dismissed`
（`AgentCommands.cmdAct`）。本实验的问题很直接：**仪表装了这么久，它说了什么？**

外加一条来自实跑的假说（待验）：

> 会**拉起一个新编辑器**的动作（点开撰写页、点进一个输入框）导致主屏键盘被抢。

机制上它说得通，且与 `ARCHITECTURE §8.1` 自洽：全系统只有一个 IME 实例、
`mCurClient` 是单数，副屏编辑器一旦拿到输入焦点，IMMS 就把绑定移过去。

## 2 · 第一个结果：仪表一次都没响

```
步数合计 126；带 ime 字段的 45；ime.dismissed=true 的步数 0
```

**45 步，0 次。** 而我们**知道**收起真实发生过（E12 是用户（我）本人在录制现场报告的）。

所以这不是「没发生」，是**仪表没抓到**。

## 3 · 第二个结果：用两层采样把它夹出来

有两个粒度不同的采样源：

| 源 | 采样时机 | 字段 |
|---|---|---|
| `env.json` | 每步**开头**（loop 调 `state()`） | `ime_present` |
| `act_resp.json` | 每次 `act` **前后**各一次 | `ime.before` / `ime.after` |

在 `env` 层找 `True → False` 的相邻步，再用 `act` 层把区间夹窄。全仓库 **7 次**：

| run | 转换 | 前一步动作 | 消失落在哪 |
|---|---|---|---|
| 2026-08-05T23-56-38 | 04→05 | CLICK LinearLayout (1533ms) | — 该 run 早于仪表 |
| 2026-08-06T16-51-30 | 02→03 | CLICK Button (1036ms) | — 该 run 早于仪表 |
| 2026-08-06T16-51-30 | 05→06 | CLICK EditText (175ms) | — 该 run 早于仪表 |
| 2026-08-07T04-37-08 | 08→09 | **无动作**（wait/解析失败步） | ③ act 之外，**且前一步根本没有动作** |
| 2026-08-07T05-31-51 | 03→04 | SET_TEXT EditText (202ms) | ④ **消失后又自行恢复** |
| 2026-08-07T05-42-53 | 02→03 | BACK (6ms) | ② 两次 act 之间 |
| **2026-08-07T05-52-07**（演示） | 04→05 | SET_TEXT EditText (331ms) | ③ **该步 act 之前**，观测/LLM 期间 |

区间编号：① 某次 `act` 之内（仪表本该抓到）· ② 两次 `act` 之间 ·
③ `act` 之外的观测/LLM 期间，其间无任何动作下发 · ④ 消失后又自行恢复。

> **四次可定位的，落在 ① 的是 0 次。**

## 4 · 两条站得住的结论

### 4.1 这个仪表在结构上抓不到它要抓的东西（确定）

`dismissed = imeBefore && !imeAfter` 只在**单次 `act` 内**采两个点。
而四次可定位的消失，**没有一次落在那个窗口里**。

不是「还没触发」，是**采样点选错了位置**。这与 E14 里
`gfxinfo` 在视频播放时恒读 0 帧、`media_session.position` 懒更新是同一类问题：
**读数本身没错，但它测的不是那条链路 / 不是那个时间尺度。**

README 原来的说法「尚未定位到具体是哪个动作触发」不够准确 ——
准确的说法是「**现有仪表无法定位**」。

### 4.2 现有数据不支持「某个动作抢走了键盘」，反而轻微指向反面（否定结论）

- 演示那次：`env` 在 step-04 开头读到 `True`，同一步 `act` 时已是 `False`。
  中间只有一次 observe 和一次 LLM 调用，**agent 一个动作都没下发**。
- 04-37-08 那次：前一步**压根没有动作**（wait 或解析失败步），键盘照样没了。
- 05-31-51 那次：`env` 读到 `False`，可下一次 `act` 时键盘**自己回来了** ——
  说明它在比一步更短的尺度上振荡。

**§1 那条假说没有被证伪，但也拿不到任何支持。**

## 5 · 为什么这批数据注定定不了因果

采样间隔就是 **LLM 延迟**。四个带仪表的 run 里单步 `llm_ms` 从 **1.5 s 到 149 s**，
多数在 10–40 s。演示那次夹住消失的那一步（step-04）是 **18.7 s**。

> 用一个十几秒的窗口，去归因一个毫秒级的事件 —— 方法上不成立。

那十几秒里用户在主屏做什么完全不受控（打完一个词、点了别处、app 自己收键盘），
而这些比 agent 的动作更可能是原因。**继续挖 trajectory 挖不出答案，得换实验形态。**

## 6 · 能定这件事的实验（设计，未跑）

形态与 E15 相同 —— E15 也是靠 `input tap` 把打字侧自动化之后才把条件对齐的。

- **轮询**：后台线程每 ~50 ms 读一次 display 0 的 IME 窗口，带时间戳
  （`tools/exp_secondary_contamination.py` 里已有轮询骨架）
- **主屏**：保持一个输入框聚焦、键盘弹着，`input tap` 自动敲键，不需要真人
- **每轮只下发一个动作**，记录动作时刻 `t0`，观察 IME 是否在 `t0 + N ms` 内消失
- **分组**：`CLICK` 打在 EditText 上 / `FOCUS` 打在 EditText 上 / `SET_TEXT` 打在
  EditText 上 / `CLICK` 打在 Button 上 / 会重建 Activity 的动作
- **阴性对照组（必须有）**：不下发任何动作，只等同样长的时间 ——
  §4.2 已经说明「什么都不做也会消失」是一个真实可能，没有这一组的话
  任何阳性结果都可能是它的假象
- n=20 每组

这个实验同时回答两件事：**键盘是被哪一类动作抢走的**，以及
**它是不是根本不需要动作就会消失**。后者若成立，README 里
「唯一确认的用户可见代价」这句话的**归因**需要改写（现象仍然成立）。

## 7 · 限度

- 全部结论来自 4 个带仪表的 run，且都是 Gmail 任务、`deepseek-v4-flash`、同一台模拟器。
- 7 次转换里 3 次因为 run 早于仪表而无法定位，可用样本实际只有 4 次。
- `env` 层与 `act` 层之间还夹着 observe / compress / 验证重读，本文把它们统称为
  「无动作区间」—— 它们都是只读调用，但**「只读调用不夺焦点」本身没有被单独验证过**。
- 未观测「键盘怎么回来的」：E12 记的是用户手动点了一次，
  而 05-31-51 那次显示它也可能自行恢复。两者没有区分开。
