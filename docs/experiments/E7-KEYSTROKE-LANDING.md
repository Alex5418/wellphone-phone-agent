# E7 · 打扰窗口期间用户击键的落点

**日期** 2026-08-06 · **标签** `[非root可复现]`（uid=2000 shell）· API 34 · scrcpy VirtualDisplay
**脚本** `tools/exp_keystroke_landing.py`（四分组，可复跑）

前面所有实验测的都是「焦点在谁手里」。这一个测的是**用户敲的字最后进了哪个输入框** ——
它是唯一直接对应验收标准（用户当前正在进行的交互不被中断）的实验。

> ⚠ **适用范围（后补）**：本实验用 `input text` 注入，那是**物理键盘**语义。
> **软键盘（点屏幕）的行为完全不同 —— 一次污染都没出现，见 E8。**
> 下文所有"污染"结论只在外接键盘场景成立。E8 给出按输入方式重新分级的结论。

## 场景

| | |
|---|---|
| 主屏 display 0 | composetest（Compose 写信界面，Body 输入框聚焦，IME 弹起） |
| 副屏 display 2 | Settings 搜索页，**搜索框已聚焦** —— 即 agent 的工作区 |
| 击键注入 | `adb shell input text`，**不带 `-d`**：走全局焦点，与物理键盘同语义（键盘没有屏幕归属） |
| 注入速率 | 实测 39 ms/字符（约 26 字/秒，快速打字） |

计数方式：动作前后分别读两块屏上所有可编辑节点的文本长度，取差值。
hint 不算内容（空 EditText 的 `getText()` 返回 hint 是已知坑）。

---

## 1 · 结果

| 分组 | 条件 | 发出 | 主屏 | **副屏（agent 工作区）** | 丢失 | 打扰窗口 |
|---|---|---|---|---|---|---|
| A 对照 | 只打字，agent 不动 | 120 | 120 | **0** | 0 | — |
| B 阳性对照 | 动作 + `restore=false` | 120 | 64 | **56** | 0 | 5 ms |
| C 护栏 ①  | 动作 + `restore=true` | 120 | 114 | **6** | 0 | 205 ms |
| C 护栏 ② | 同上 | 120 | 99 | **21** | 0 | 612 ms |
| C 护栏 ③ | 同上 | 120 | 114 | **6** | 0 | 228 ms |
| D 最坏 | 全局配置变更 + `restore=true` | 200 | 71 | 0 | **129** | 1421 ms |
| E 无归还对象 | 主屏无焦点持有者 | 120 | 0 | **120** | 0 | 9 ms |

A 组是**仪表校验**：污染为 0、丢失为 0，说明计数器没有锁死、场景本身不产生污染。
没有 A 和 B，C 组的"污染很少"什么都证明不了（丢字计数器锁在常量上的教训）。

## 2 · 结论一：bug 是真的，而且不归还时**没有上界**

B 组复现了它：120 个字符里 **56 个进了 agent 的搜索框**。

关键在于：**动作本身只有 5 ms，污染却有 56 个字符。**
不归还的话焦点再也不回来，此后用户敲的每一个字都落到副屏 ——
污染量不是与动作时长成正比，而是与**用户还要继续打多久**成正比。无上界。

这是正确性故障而不是体验问题：agent 会基于被污染的工作区继续决策。

## 3 · 结论二：归还把污染变成**有界**，但不是零

C 组三次：打扰窗口 205 / 612 / 228 ms → 污染 6 / 21 / 6 字符。

按 39 ms/字符预测：5.3 / 15.7 / 5.8 —— 实测 6 / 21 / 6，同一量级且随窗口线性变化。

> **污染字符数 ≈ 打扰窗口 ÷ 打字速率**

所以归还的作用要如实描述：**它把污染从「无上界」压成「与打扰窗口成正比」，
但压不到零。** 只要动作分发路径会夺焦点，窗口就不可能为 0。

由此，减少污染的唯一途径是**缩短打扰窗口**。而 D2 已经量过，窗口取决于
主屏焦点节点能不能被 id 直接定位：Chrome（有 `url_bar` id）12 ms，
composetest（Compose，无 id）313 ms。按上面的公式，前者对应 **0–1 个字符**。
本次未能补上 Chrome 主屏的对照（见 §6）。

第二次 C 组的 612 ms 已经超过 `DISTURB_BUDGET_MS`（500 ms）——
排除规则会把这个目标拉黑。这说明那条预算不是拍脑袋定的：
它对应的正是「一次动作污染十几个字符」这个量级。

## 4 · 结论三：最坏情况下是**丢字**，量级更大

D 组（切换深色主题，触发全局配置变更）：200 个字符里 **129 个凭空消失**（65%）。
没有污染是因为副屏那一页没有输入框 —— 若有，这 129 个就会变成污染。

丢失量（129）远大于按打扰窗口预测的值（1421 / 39 ≈ 36）：
全局配置变更会重建所有 Activity，**输入法连接被一起拆掉**，
焦点还回来之后用户还要等 IME 重新挂上。**损失延续到打扰窗口之外。**

这条独立支持了 ARCHITECTURE §5 把这一族目标 ⛔ 排除的决定：
按验收标准，用户丢 129 个字符（约 5 秒的输入）不是"边界"，是硬失败。

## 5 · 结论四：`no_primary_focus` 不是良性状态

E 组是个意外：主屏当时没有输入焦点持有者，设备侧的归还逻辑判定
「没有东西可还」（`attempted: false, reason: no_primary_focus`）并跳过 ——
结果 **120 个字符 100% 落进 agent 工作区**。

跳过归还本身没错（确实没有可还的目标），但**这个状态的危险程度被低估了**：
主屏没有焦点持有者，等价于 agent 的窗口就是全局焦点持有者，
此时用户敲的任何东西都进 agent 的工作区。

现状：`self_check` 已把 `primary_focus_lost` 报为异常并写进 observation。
建议（未实施）：这条异常应当升级为**动作前的阻断条件** ——
主屏没有焦点持有者时，动作要么推迟，要么先把焦点做出来再执行。

## 6 · 未验证 / 本次没做到

- **Chrome 主屏（id 路径，12 ms 窗口）的污染量**。尝试过，但 Chrome 的 URL 栏
  没能稳定获得焦点，那一次跑成了 E 组。§3 里 0–1 个字符是**按公式外推**，不是实测。
- 真实物理键盘（本实验用 `input text` 模拟，走的是同一条全局焦点路径，
  但不排除 IME 层面存在差异）
- 真机（非模拟器）
- 多次重复的统计量（每组只跑了 1–3 次，只够看量级，不够给方差）

## 7 · 复跑方法

```bash
# 主屏 composetest 输入框聚焦、IME 弹起；副屏 Settings 搜索页、搜索框聚焦
python tools/exp_keystroke_landing.py --arm A --chars 120   # 先验计数器
python tools/exp_keystroke_landing.py --arm B --chars 120   # 必须复现污染
python tools/exp_keystroke_landing.py --arm C --chars 120   # 护栏
python tools/exp_keystroke_landing.py --arm D --chars 200   # 最坏情况
```

**B 组不可省。** 只跑 C 看到"污染很少"证明不了任何事 ——
可能是护栏有效，也可能是这套测法根本测不出污染。
