# E9 · 中文拼音连打时后台跑 agent —— 归还与否的对照

**日期** 2026-08-06 · **标签** `[非root可复现]` · API 34 · scrcpy VirtualDisplay
**脚本** `tools/exp_pinyin_composing.py` · **截图** `shots/E9-restore-{true,false}-after.png`

E8 说明软键盘路径不会污染 agent 工作区，但那测的是**英文逐字提交**。
中文拼音不一样：一串拼音在上屏之前一直处于 **composing 态** ——
未提交的拼音串、候选条、分段，全是 IME 维持的中间状态。
**中间状态比已提交的文字脆弱得多**，这才是软键盘场景下真正该测的东西。

> ⛔ **本文的因果归属已被 E10 更正（2026-08-06）**：下面两组对照里，
> **动作类型与归还开关同时变了**，而且每组只跑一次，于是把「导航点击造成的打断」
> 记到了「不归还」头上。表格里的数字没错，结论错了 ——
> **决定因素是副屏有没有发生窗口 / Activity 变更，归还只能降低概率、不能消除**
> （实测归还组 3 次仍破 1 次）；纯焦点抢夺（滚动类动作）根本不打断中文输入。
> 详见 `E10-COMPOSING-BREAK-CAUSE.md`。

## 场景

| | |
|---|---|
| 主屏 display 0 | composetest，Gboard **中文拼音**（zh-CN，通过 Gboard 设置加装） |
| 副屏 display 2 | Settings 显示设置页 |
| 用户行为 | 逐键点屏幕连打 `zhonghuarenmingongheguo`，**全程不提交** |
| agent 行为 | 打字进行到一半时，副屏连跑三步（Screen timeout → 30 seconds → Navigate up） |
| 唯一变量 | `restore=true` / `false` |

> 三步是逐个 `act` 下发的，不走 loop —— loop 里 `restore=True` 是写死的护栏、没有开关，
> 而阳性对照必须能把它关掉。下发的是**与 loop 完全相同的设备侧调用**。

## 结果

| 判据 | `restore=true` | `restore=false` |
|---|---|---|
| 1. 键盘还在不在 | ✓ 在 | ✓ 在 |
| 2. 候选条 | **中中华人民共和国**（整词候选） | **过 国 果 锅 郭 國**（只剩最后一个音节） |
| 3. 光标 | 13→35，随输入前进，未跳 | 13→16，随输入前进，未跳 |
| 4. 拼音串 | `zhong zhong hua ren min gong he guo` **全带下划线**（仍在 composing） | `zhonghuarenmi` **已上屏**（无下划线）+ 仅 `guo` 在 composing |
| 分段空格 | 保留 | **消失** |
| 丢字 | **0** | **7 个**（续打 `mingongheguo` 只落到 `miguo`） |
| 三步的打扰窗口 | 236 / 131 / 168 ms | **15 / 12 / 22 ms** |

> `restore=true` 那一列开头多出的一个 `zhong` 是上一轮手工调试残留，不是本次输入产生的；
> `restore=false` 这一轮跑前已 `force-stop` 清空。

截图是这条结论的主要证据（见 `shots/`）：一眼能看出下划线范围与候选条内容的差别。

## 结论

### 1 · 归还与否，在中文输入上的差别是**质变**，不是程度差别

`restore=true`：整串拼音仍在 composing，候选条跟着长到「中中华人民共和国」，
用户按下一步选词就能上屏 —— **交互完全没有被打断**。

`restore=false`：焦点一离开，IME 就把未上屏的拼音**强制提交成裸拼音**
（下划线消失、分段空格消失），候选上下文清零，之后的击键开了一个新的 composing 段。
用户回头看到的是一串没法选词的字母，只能删掉重打。

E8 里"软键盘不会污染、顶多丢几个字"的结论，**对中文输入不成立** ——
丢的不是几个字符，是**整个词组的输入进度**。

### 2 · 破坏程度与打扰窗口长短**无关**

`restore=false` 的窗口只有 12–22 ms，比 `restore=true` 的 131–236 ms **短一个数量级**，
破坏却大得多。

原因：composing 的破坏是**一次性事件**，不是持续过程。
焦点一旦离开，IME 走 `finishComposingText` 把中间态提交掉；这一步发生了就回不去，
之后焦点回不回来都一样。

**所以归还的价值不是"缩短窗口"，而是让 IME 根本来不及走到解绑那一步。**
E7 得出的「污染 ∝ 打扰窗口」只适用于外接键盘的字符流；
对 IME 中间态，正确的模型是**二值的：断了，或没断**。

### 3 · 这条独立支撑「归还必须与动作原子绑定」

如果归还是"动作之后另发一条命令"，中间就有一段真空 —— 对字符流只是多丢几个字，
对 composing 态却足以让 IME 完成解绑。**原子绑定不是洁癖，是这条实验的直接要求。**
