# 焦点归还实验 · 结论报告

**日期** 2026-08-05 · **结论** ✅ A 档通过 · **标签** 非root可复现 / API 34 / scrcpy VirtualDisplay
**详细数据** 见 `EXPERIMENTS.md` E6 章节

---

## 一句话

**副屏 Agent 执行动作后立即对主屏输入焦点节点补发一个 `ACTION_FOCUS`，
可在 10–15 ms 内把 window 焦点拉回主屏，用户打字全程无中断、无丢字、无需触碰输入框。**

---

## 背景：这个实验要解决什么

此前已实证（E4）：**任何**通过无障碍框架发出的动作，都会把全系统唯一的 window 焦点
夺到目标窗口所在的屏幕。副屏 Agent 一动，主屏用户的输入就断。
连动作实际未生效（`result=false`）时也照夺 —— 抢焦点发生在**动作分发路径**，
与动作是否产生效果无关。

由此曾判定：主线方案「虚拟屏隔离 + a11y 动作」在"不打扰"这一硬指标上不成立。

本实验验证的假设是：**既然焦点可以被抢走，那它也可以被抢回来。**

---

## 结果

四轮对照。主屏 Dialer 搜索框真人打字，副屏 Settings 执行 `SCROLL_FORWARD`。

| Run | 归还 | 副屏动作 | 主屏 window 焦点 | 触发后打进的字符数 | 往返耗时 |
|---|---|---|---|---|---|
| 1 基线 | ✗ | 真实生效 | **丢失（null）** | **0** | — |
| 2 核心 | ✓ | 真实生效 | 全程保持 | **42** | **10 ms** |
| 2b 对照 | ✗ | 未生效 | **丢失（null）** | **0** | — |
| 3 复现 | ✓ | 真实生效 | 全程保持 | **62** | **15 ms** |

Run 1 与 Run 2 构成严格对照：副屏动作完全相同且都真实生效，唯一变量是归还。
**四轮之中，归还与否 = 焦点存活与否，无例外。**

肉眼判据（最终判据）：Run 1 / 2b 字在触发瞬间断掉且不点输入框无法恢复；
Run 2 / 3 字全程连续，副屏动作同时真实生效。

三项指标：往返耗时 10–15 ms（及格线 < 100 ms）、丢字 0（及格线 ≤ 2）、
IME 全程未断开（原定生死线）。

---

## 机制：焦点不是被"还"回来的，是被"再抢"回来的

最反直觉的一条观测：**`ACTION_FOCUS` 返回 `false`，归还却成功了。**

1. 主屏输入框的 **view 焦点从未丢失** —— 焦点被夺走后它的 `isFocused` 仍是 `true`。
   丢的只有 **window 焦点**。二者是不同层级的概念。
2. 所以对一个已聚焦的节点再发 `ACTION_FOCUS`，是空操作，返回 `false`。
3. 但**抢焦点发生在动作分发路径，与动作是否生效无关**（E4 结论）。
   这次分发的目标是一个主屏节点 → window 焦点被拽回主屏。

于是此前那条致命结论被反向使用：

> **E4：任何 a11y 动作都会把焦点带到目标窗口 —— 这是故障。**
> **E6：任何 a11y 动作都会把焦点带到目标窗口 —— 这是手段。**

**推论：`ACTION_FOCUS` 是最优的归还手段，恰恰因为它什么都不做。**
它不改变任何 UI 状态、不移动光标（实测 `sel` 前后完全一致），
却能把 window 焦点拉回来 —— 一个零副作用的纯焦点拉取原语。

---

## 这意味着什么

**冲突没有被消除，而是被压缩到了用户感知阈值以下。**

这是一个诚实的、可讲的论述：单焦点是 Android 的框架级约束，
不可能在不改系统的前提下消除。但焦点丢失的**持续时间**是可控的，
把它从"永久中断、必须手动点回输入框"压到 10–15 ms 之后，
它在用户那里就不再是一次打扰。

主线方案「虚拟屏隔离 + a11y 动作」由此**条件性成立**。

---

## 尚未证明的部分（勿外推）

| 未覆盖 | 风险 |
|---|---|
| 只测了 `SCROLL_FORWARD` 一个动作 | **最高**。已知所有动作都抢焦点，但只证明了归还对其中一个有效 |
| 副屏动作未引发 Activity 跳转 | 跳转场景下 IME 可能真的断开，届时"能否自动重连"仍是未知 |
| 单次动作 | 连续 / 高频动作下的表现未测 |
| 仅模拟器 API 34 | 未在真机复现 |
| 用户此刻正在输入 | 主屏无输入焦点时归还行为未定义 |

**关于 IME**：本次实测中 IME 根本没有断开，比预设的成功形态更强 ——
但这也意味着「IME 断开后能否自动重连」这个原定的最大不确定性，
**本实验并没有回答它**，只是绕过了它。

## 附：实验过程中查出的五个静默失效

这些在代码里都不报错，且**其中两个会让结论完全反向**。记录在此供后续复用。

1. **`findFocus(FOCUS_INPUT)` 会命中软键盘窗口内的按键节点。**
   软键盘也是主屏上的一个窗口，遍历先到先得会拿到输入法的按键而非用户输入框。
   → 不修则归还打在键盘按键上，得出"跨屏焦点不联动、GUI 路线封死"的**假结论**。
2. **"取文本最长的 EditText"作为丢字计数器是错的。**
   搜索栏容器的提示语（24 字符）比用户实际输入更长且是常量
   → **Δ 恒为 0 → 得出"一个字没丢"的假结论**。应优先取 `isFocused` 的节点。
3. **空 `EditText` 的 `getText()` 返回 hint 而非空串。**
4. **`actionList` 未登记某动作 ≠ 该动作不可用。** 定位逻辑需带"爬不到就用原节点"的兜底。
5. **`scroll=true` 不代表此刻有滚动余量。** 折叠工具栏页面真正滚动的是外层容器。

**方法论两条**：

- **对照要与实验轮"同状态"，而非"同协议"。** 基线跑完后环境已漂移，
  补一轮同状态、只翻转唯一变量的对照，才把因果钉死。
- **测量工具本身要先验证。** 计数器一度锁在常量上，
  它会稳定输出"丢字 0"这个正确答案 —— 正确答案 + 错误来源，是最贵的那种错。
