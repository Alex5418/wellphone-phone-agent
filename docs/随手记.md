=========== 2026-08-05 焦点归还实验（EXP-FOCUS-RESTORE / experiments/EXPERIMENTS.md E6）===========

[E6] ✅ 通过 · A 档 [非root可复现 · API 34 · scrcpy VirtualDisplay]
副屏动作后立即对主屏输入焦点节点发 ACTION_FOCUS，10-15ms 把 window 焦点拉回 display 0。
打字全程不断、丢字 0、不用手动点输入框。

四轮对照（主屏 Dialer 搜索框 / 副屏 Settings SCROLL_FORWARD）：
  Run 1  不归还  动作ok=true   焦点→null      触发后 Δ=0    ← 基线，复现已知失败
  Run 2  归还    动作ok=true   焦点全程 Dialer 触发后 Δ=42   total=10ms
  Run 2b 不归还  动作ok=false  焦点→null      触发后 Δ=0    ← 我加的同状态对照
  Run 3  归还    动作ok=true   焦点全程 Dialer 触发后 Δ=62   total=15ms
Run1 vs Run2 是严格对照：同动作、都生效，唯一变量是归还。


★ 最关键的一条：ACTION_FOCUS 返回 focusOk=false，归还却成功了。

为什么：view 焦点压根没丢过。焦点被夺走之后那个 EditText 的 isFocused 仍然是 true，
丢的只有 window 焦点。所以对已聚焦节点再 FOCUS 一次是空操作，返回 false。
但是——按我之前那条结论「抢焦点发生在动作分发路径，与动作是否生效无关」——
这次分发的目标是个 display 0 的节点，于是 window 焦点被拽回了 display 0。

所以焦点不是被"还"回来的，是被"再抢"回来的。
以前那条致命结论反过来用了：
  之前：任何 a11y 动作都会把焦点带到目标窗口 —— 这是故障
  现在：任何 a11y 动作都会把焦点带到目标窗口 —— 这是手段

推论：ACTION_FOCUS 是最优归还手段，恰恰因为它什么都不做。
返回 false、不改 UI、不移动光标（sel 前后都是 86..86 / 8..8），
纯粹一个零副作用的焦点拉取原语。原本备选的 ACTION_CLICK（会移动光标）用不上了。

Run 2b 还顺便又复现了一次老结论：那轮 ok=false（列表在底部没滚动），焦点照样被夺走。
而且那轮 mInputShown 全程 true，键盘根本没收起、InputConnection 还连着，
但字就是打不进去 —— 「IME 收起与输入中断解耦」第三次独立复现。


[指标②的意外] md 原本担心「IME 断过一次能不能自动重连」，说这是生死线。
实测中 IME 根本没断开：mServedView 全程指向那个 EditText，mInputShown 全程 true。
比预设的成功形态更强。
但反过来说：「IME 真断开后能不能重连」这个问题本次没有回答。
如果以后遇到真会导致 IME 断开的场景（比如副屏动作引发 Activity 跳转），这条仍然是未知。
不能拿 E6 的结论去覆盖。


[适用边界 · 别外推] 现在只验证了：
  模拟器 API 34 一台、SCROLL_FORWARD 一个动作、副屏未跳转 Activity、单次动作。
  CLICK / SET_TEXT / LONG_CLICK 全没测。真机没测。
最大风险：R3 证明了所有动作都抢焦点，E6 只证明了归还对其中一个动作有效。
做进原子封装之前必须先把动作维度补齐。


----------- 这次实验踩到的静默失效（都差点让结论反向）-----------

1. findFocus(FOCUS_INPUT) 会抓到软键盘里的按键。
   软键盘也是 display 0 上的一个窗口，遍历先到先得，
   拿到的是 com.google.android.inputmethod.latin:id/key_pos_header_... 这种 Gboard 的键。
   不修的话归还会打在键盘按键上，然后得出「跨 display 焦点不联动 → C 档 → GUI 路线封死」
   —— 一个会让我砍掉一条其实还活着的路线的假结论。
   修法：跳过 AccessibilityWindowInfo.TYPE_INPUT_METHOD，优先取 isEditable 的节点。

2. 「取文本最长的 EditText」当计数器是错的。
   Dialer 那个 open_search_bar 的文本是提示语 "Search contacts & places"（24 字符），
   比我实际打进去的内容还长，永远赢。而提示语是常量 → Δ 恒为 0 →
   跑完会看到「一个字没丢」然后以为方案成立。计数器压根没在看我打字的那个框。
   修法：优先取 isFocused 的节点，长度只做兜底。

3. 空 EditText 的 getText() 返回 hint 不是空串。
   清空后读出来是 len=24 text='Search contacts & places' sel=-1..-1。
   以后自动化判空别用 text.isEmpty()，得看 textSelectionStart == -1。

4. actionList 里没登记某动作 ≠ 那个动作不能用。
   recycler_view 的 actionList 里没有滚动动作，已有的 DO 指令那套
   「向上爬找支持该动作的父节点」会一路爬到 null 然后静默不发（result=null node=null）。
   但直接对它 performAction(SCROLL_FORWARD) 返回 true 而且真的滚了。
   定位逻辑必须带「爬不到就用原节点」的兜底。DO 指令这个 bug 还没修。

5. scroll=true 不代表此刻有滚动余量。
   Display Settings 是折叠工具栏 + 列表的双层结构，真正在滚的是外层 ScrollView(content_parent)，
   内层 recycler_view 内容装得下、自己没有滚动范围。两个容器两个方向全返回 false。
   重置副屏状态别猜滚动容器，直接 am force-stop 再重启 Activity。


----------- 方法论上的两条 -----------

* 对照要和实验轮"同状态"，不是"同协议"。
  Run 1 跑完副屏列表已经被滚到底了，Run 2 的成功一度没法排除
  「这次动作本来就没夺焦点」这个解释。补了 Run 2b（同状态、只翻转归还这一个变量）
  才把因果钉死。md 的协议里没有这一轮，是必须加的。

* 测量工具本身要先验证。
  计数器一开始锁在提示语常量上，如果不先验一遍，它会稳定输出「丢字 0」这个正确答案，
  而它测的根本不是那个框。正确答案 + 错误来源 = 最贵的那种错。
